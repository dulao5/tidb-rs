# Differences from TiDB v8.5.8 visible to users

tidb-rs is a function-by-function port of Go TiDB **v8.5.8** (`8b857efa2`). By default it behaves exactly like v8.5.8, including its bugs. This page lists the places where a user can see different behavior. Internal deviations that cannot be observed through SQL or the wire protocol are recorded in each block's `specs/<block>/spec.md` §4, not here.

Every row of the go-fix, deliberate-deviation, observability, plan cache and privilege-check tables below is also a ruling in the machine-readable divergence ledger [`docs/testing/rulings.toml`](testing/rulings.md) (id, approver, re-open trigger). Add a new deviation to both.

## Upstream fixes ported from TiDB master (go-fix)

Following the constitution (article 1, item 2), tidb-rs ports security and data-correctness fixes that are on TiDB master but were not backported to `release-8.5`. The govec vectors for these cases are generated from a patched v8.5.8 (see `govec/fixes/README.md` in tidb-rs-tracker).

| Upstream fix | v8.5.8 behavior | tidb-rs behavior | Compatibility impact |
|---|---|---|---|
| [pingcap/tidb#62892](https://github.com/pingcap/tidb/pull/62892) (labelled `compatibility-breaker` upstream; not in any 8.5 release) | `SET [SESSION] tidb_redact_log = …` succeeds, but actually switches redaction for **every session on the instance**, and is not persisted ([tidb-rs #62](https://github.com/dulao5/tidb-rs/issues/62)). | `tidb_redact_log` has **GLOBAL scope only**. `SET tidb_redact_log = ON` without a scope (= SESSION) and `SET SESSION …` fail with error 1229; use `SET GLOBAL tidb_redact_log = …`, which is cluster-wide and persisted. Same as TiDB master for user sessions. | **Breaking.** Scripts that set it without `GLOBAL` get an error. In a mixed Go/tidb-rs cluster both sides store the value in `mysql.global_variables` in the same format and read each other's `SET GLOBAL`. |
| [pingcap/tidb#65884](https://github.com/pingcap/tidb/pull/65884) | `SET tidb_opt_fix_control = '123:'` (colon with no value) fails with `ERROR 1105 runtime error: index out of range …` (an internal panic, recovered per statement); nothing is set. | The value after the colon is empty; no error. | None (an error becomes a success). |

Same as TiDB release-8.5 after v8.5.8. | None. |
| [pingcap/tidb#71844](https://github.com/pingcap/tidb/pull/71844) and [pingcap/tidb#72214](https://github.com/pingcap/tidb/pull/72214) (issue pingcap/tidb#71858; on `release-8.5` after v8.5.8 as `4f61995df8` and `84040e1f0a`; **security**, credential leak) | `ast.RedactURL` (the value `SELECT @@global.tidb_cloud_storage_uri` shows) keeps the userinfo (`s3://user:pass@…`), the fragment and every query option it does not know; it masks only `access-key` / `secret-access-key` / `session-token` for `s3`/`ks3` and `sas-token` for `azure`/`azblob`, so `oss` keys, Azure `account-key` / `encryption-key` / `endpoint` (which can hold a SAS), S3/GCS `endpoint` and GCS `credentials-file` are shown in clear. The stored value is not changed. | None for query results. Only the redacted display of the URI changes (e.g. `noop://blackhole?access-key=…` reads back as `noop://blackhole`); tools that parse the displayed value for non-secret options of unknown names no longer see them. |

## Deliberate deviations from v8.5.8

| Area | v8.5.8 behavior | tidb-rs behavior | Reason |
|---|---|---|---|
| `tidb-server --redact` (log de-redaction, `DeRedact`) | A line longer than 64 KiB stops Go's `bufio.Scanner`; that line **and every line after it** are silently dropped and the command exits successfully ([tidb-rs #90](https://github.com/dulao5/tidb-rs/issues/90)). Not fixed on master. | All lines are processed. | Copying Go would silently lose data in a recovery tool; slow logs with large `INSERT` statements commonly exceed 64 KiB per line. |
| Warnings of a non-numeric string filter (`WHERE str_col`, `WHERE CAST(.. AS CHAR)`) with vectorized evaluation | `Truncated incorrect DOUBLE value: '…'` is formatted when the warning is read, from the bytes of a pooled column that may have been reused by then, so `SHOW WARNINGS` can show other bytes instead of the value (Go `toBool` over `Column.GetString`, which aliases the column; confirmed on v8.5.8 within one statement — 976 of 2,000 warnings showed another row's value — also through `c + 0` and a vectorized `CAST(c AS DOUBLE)`, and not with vectorization off; across sessions not reproduced; [tidb-rs #97](https://github.com/dulao5/tidb-rs/issues/97)). | The warning shows the value. | Reproducing it would show unrelated (possibly other sessions') data in warnings; tidb-rs has no global column pool (mapping rule M-POOL). |
| Constant propagation over YEAR columns compared with a fractional constant (`WHERE y1 = y2 AND y2 < 1.0`) | Propagation rewrites the shared constant in place (`AdjustYear` in `refineArgs`), so the original condition changes too: `y2 < 1.0` alone returns `0000`, but with `y1 = y2` it also returns `1990` and `2000` (the plan shows `lt(y2, 2001)`); `y1 = y2 AND y2 >= 0.5` loses `(1990,1990)` and `(2000,2000)` ([tidb-rs #104](https://github.com/dulao5/tidb-rs/issues/104)). | Propagation works on copies; adding `y1 = y2` does not change the rows `y2 < 1.0` returns. The `>= 0.5` case matches v8.5.8 (the `Ceil` rewrite, #99, is ported as is). | Copying Go's in-place mutation would reproduce an upstream bug that returns wrong rows; tidb-rs expressions are immutable shared values (D08.2 spec §4 item 7). |
| `tidb_schema_cache_size = 0` | `0` switches the node to infoschema v1: every table's metadata is kept in memory, nothing is evicted, and `IsV2` is false (a v1/v2 switch reloads the whole schema). Any value > 0 is the byte limit of the infoschema v2 table cache. | tidb-rs has only infoschema v2. `0` means an **unbounded** v2 table cache: tables are read from TiKV on first use (as in v2) and never evicted. Values > 0 behave as in v8.5.8 (byte limit), but the limit is charged with tidb-rs's own per-table size estimate, so the same limit holds a different number of tables. Query results are the same; only memory use and the number of meta reads from TiKV differ. The variable's value, validation and persistence are unchanged. | Owner decision: infoschema v1 is technical debt and is not ported (D06.3 spec §1.2); the cache layout is exception A3 (D06.3 spec §5.4, accepted 2026-11-14). |
| Infoschema v2 GC of old schema versions ([tidb-rs #195](https://github.com/dulao5/tidb-rs/issues/195)) | The GC (cut = the oldest schema version in use, `meta.GetOldestSchemaVersion`) deletes a table's metadata version older than the cut whenever a newer version exists, even if that newer version is above the cut. A read at the cut version (stale read, `tidb_snapshot`, `AS OF TIMESTAMP`, a statement still on that version) of a table altered after it then fails with `Table '...' doesn't exist`, and sees no foreign-key references to it. | Per table, the newest version at or below the cut is kept; only older ones are deleted (also for the foreign-key references). | Decision (D06.3, Maya + Lucky, 2026-11-14): copying Go would fail correct reads. Only reads that failed in v8.5.8 now succeed; nothing that succeeded changes. |
| Result-set column definitions of a prepared statement whose parameter appears in the select list (`SELECT ?, c ...`) ([tidb-rs #367](https://github.com/dulao5/tidb-rs/issues/367)) | The connection caches the column definitions of the statement's **first** `EXECUTE` and reuses them when a later `EXECUTE` binds a parameter of another type: after a signed first `EXECUTE`, `18446744073709551615` is sent in a signed column and the client reads `-1`; after an integer, a string is sent as garbage bytes in a `LONGLONG` column | Every `EXECUTE` sends the column definitions of its own parameters (unsigned `BIGINT` for `u64::MAX`, `VAR_STRING` for a string), the same as v8.5.8 sends for a fresh statement and as MySQL 8.0.22+ does by re-preparing when a parameter's type changes | The cache returns wrong values; constitution article 1 item 2, owner ruling 2026-11-25 (R19, R20) |

## Plan cache (exception A3)

tidb-rs has only the instance-level plan cache, shared by all sessions; Go's session-level prepared plan cache is not ported. Behavior follows Go v8.5.8 with `tidb_enable_instance_plan_cache = ON`, except for the rows below. Owner decisions of 2026-11-23 ([#305](https://github.com/dulao5/tidb-rs/issues/305)); design in [`specs/exceptions/A3-plan-cache/spec.md`](../specs/exceptions/A3-plan-cache/spec.md) §4 and §6.

| Area | v8.5.8 behavior | tidb-rs behavior | Reason |
|---|---|---|---|
| `tidb_enable_instance_plan_cache` default, and the session-level cache | Default `OFF`: prepared statements use a per-session plan cache (`tidb_session_plan_cache_size` etc. apply). `ON` switches to the shared instance-level cache. | Default **`ON`**: the instance-level cache is the only plan cache, so a new session's first `EXECUTE` can already report `@@last_plan_from_cache = 1` (a plan cached by another session). With `OFF` **nothing is cached** (`@@last_plan_from_cache` is always 0, no warning). The session-level variables (`tidb_session_plan_cache_size`, `tidb_prepared_plan_cache_size`, `tidb_prepared_plan_cache_memory_guard_ratio`) are accepted, validated and stored but have no effect, as in v8.5.8 with the instance cache on; `tidb_enable_prepared_plan_cache` still turns the cache off for the session. | Keeps Go's default experience (prepared statements hit a plan cache) without porting the session cache. In a mixed Go/tidb-rs cluster the persisted global value is the one written by the node that bootstrapped the cluster. |
| `ADMIN FLUSH INSTANCE PLAN_CACHE` | With the instance cache on it does **not** clear it: it clears only the current session's (unused) session cache and records a timestamp the instance cache never reads, so `EXECUTE` in any session still reports `@@last_plan_from_cache = 1` afterwards ([tidb-rs #307](https://github.com/dulao5/tidb-rs/issues/307)). | Clears the instance-level cache: the next `EXECUTE` of every statement re-optimizes (`@@last_plan_from_cache = 0`). Statements already running keep their plan, and a plan whose optimization started before the flush is not added afterwards. As in v8.5.8, when `tidb_enable_prepared_plan_cache` is `OFF` in the session that runs it, the statement only returns the warning `The plan cache is disable. So there no need to flush the plan cache` and clears nothing. Other validation and warnings (`GLOBAL` scope rejected, warning when the plan cache is disabled for the session) are as in v8.5.8. Requires `SUPER` (owner decision 2026-11-24, ruling R18): in v8.5.8 `buildAdmin` returns for `FLUSH ... PLAN_CACHE` (like a few other ADMIN statements) before it adds the `SUPER` check that most ADMIN statements get, which was harmless there because the statement did not touch the instance cache; now that it clears the cache for every session on the node, it requires `SUPER` like most ADMIN statements. tidb-rs has no privilege checks yet (user identity and privileges are not ported), so until then any connected user can run it; the check comes with the privilege port. | An administrative statement that silently does nothing is a Go defect; corrected under constitution article 1, item 2. |
| Sharing of cached plans between accounts | The cache key concatenates user name, host name and database name without separators, so two accounts such as `'a127.0.0.'@'%'` and `'a'@'127.0.0.%'` share cached plans (privileges are re-checked on a hit, so this is not a privilege bypass) ([tidb-rs #308](https://github.com/dulao5/tidb-rs/issues/308)). | Key fields are length-prefixed: different accounts never share a cached plan. Visible only through `@@last_plan_from_cache` when names concatenate to the same string. | Go's code intends plans not to be shared between users. |

Implemented so far (first stage): prepared statements whose plan runs on the new stack (point gets by primary key or unique index; the plans of table reads are cached but their executor is not ported yet). Statements answered by the prototype use no plan cache (`@@last_plan_from_cache` is 0 after them). The global values of these variables cannot be changed on tidb-rs yet (`SET GLOBAL` does not reach the new stack, it uses the compiled defaults).

The eviction period of the instance plan cache is the same as Go v8.5.8: fixed at 30 seconds, no variable (owner decision, 2026-11-23). The 30 seconds is the period of the check (which evicts the least recently used entries only when the cache is over its soft limit), not a lifetime: there is no per-entry TTL.

## Privilege checks (D04.1)

Owner decisions of 2026-11-26 ([#438](https://github.com/dulao5/tidb-rs/issues/438)) and, for the `LATERAL` `ON` clause (R36), 2026-11-28 ([#482](https://github.com/dulao5/tidb-rs/pull/482)); design in [`specs/D04.1-privilege/spec.md`](../specs/D04.1-privilege/spec.md) §5 and §6 and [`specs/D09.3-join-build/spec.md`](../specs/D09.3-join-build/spec.md) §4.8 and §9.1. Implemented across `tidb-privilege`, `tidb-planner`, `tidb-session`, `poc-domain`, and `poc-session` (both the new stack and the PoC fallback path share the cluster-loaded `mysql.*` privilege cache kept fresh via etcd `/tidb/privilege`).

| Area | v8.5.8 behavior | tidb-rs behavior | Reason |
|---|---|---|---|
| Table-level `SELECT` check on queries without column references & `GROUP BY` column/alias privileges (R29) | `buildDataSource` and `buildMemTable` register no `SelectPriv`; only referenced columns and lowercase `"count"` are checked. Users without `SELECT` on `t` can run `SELECT 1`, uppercase `COUNT(*)`, `SUM(1)`, `EXISTS(SELECT 1 ...)`, unreferenced-column joins/CTEs/unions, `EXPLAIN` / `EXPLAIN ANALYZE SELECT 1`, `INSERT ... SELECT 1`, `CREATE VIEW ... AS SELECT 1`, and view queries without caller grant on the view; secondary-unique-index `PointGet` `IsTableDual` overflow also skips `WHERE` column checks. In addition, `resolveGbyExprs` guards `checkColPriv` during AST resolution while `rewriteGbyExprs` omits it, so a partial-column `SELECT(a)` user can run both `SELECT COUNT(*) FROM t GROUP BY b` and `SELECT COUNT(*) AS b FROM t GROUP BY b` (where `b` is an ungranted column of `t`). | Always-on table-read `SelectPriv` (`column = "*"`, satisfied by global/db/table `SELECT` or `SELECT(col)` on at least one column) registered at every data-source, memtable, view, and `PointGet` `SELECT` boundary, with **no compatibility switch**. Unauthorized queries fail with error `1142` (and `PREPARE -> REVOKE -> EXECUTE` re-checks the non-empty `visit_infos`). Both the new-stack planner (`rewrite_gby_exprs`) and the prototype also enforce column `SELECT` privileges on `GROUP BY` items, so a partial-column `SELECT(a)` user fails with `1143` on both `SELECT COUNT(*) FROM t GROUP BY b` and `SELECT COUNT(*) AS b FROM t GROUP BY b` (folded into R29, owner decision 2026-11-28). **Mixed-cluster note:** behind a shared load balancer with unpatched Go v8.5.8 nodes, an under-privileged account running these queries is rejected with `1142`/`1143` by `tidb-rs` while allowed by Go v8.5.8; this divergence is explicitly accepted by the owner (2026-11-26, 2026-11-28). | Constitution article 1, item 2 (security exception); owner decisions 2026-11-26 (D1 option A, R29, #438) and 2026-11-28 (GROUP BY column/alias rejection folded into R29). |
| Table-denied (`1142`) vs column-denied (`1143`) precedence (R30) | A user with zero `SELECT` privilege on `t` gets `1143` (`for column 'a' in table 't'`) on `SELECT a FROM t`, versus `1142` on `SELECT a FROM nosuch`, exposing table existence. | Table/view access (`1142`) is checked first (and before view expansion / `1356`). Users with no `SELECT` access on the table always receive `1142`; error `1143` is returned only when the user already has table read access (e.g. `SELECT(a)`) but lacks privilege on a specific column (e.g. `b`). | Closes the `1143` vs `1142` table-existence oracle; owner decision 2026-11-26 (D3 option A, R30, #438). |
| Missing-table check on read statements (`1142` vs `1146`, R31) | `tableByName` checks `AllPrivMask` (`column = ""`) when a table does not exist, so a user holding non-`SELECT` grants (e.g. `INSERT ON test.*`) gets `1146 Table 'test.nosuch' doesn't exist` on `SELECT`. | Read statements check `SelectPriv` (`column = "*"`) on missing tables; users without read access always receive `1142` instead of `1146`. | Closes the `1146` missing-table enumeration oracle; owner decision 2026-11-26 (D4 option A, R31, #438). |
| Reading hidden column `_tidb_rowid` (R32) | `buildDataSource` leaves `OrigTblName` empty on `_tidb_rowid`, so both zero-privilege and partial-column `SELECT(a)` users can read `_tidb_rowid`. | Reading `_tidb_rowid` requires full-table (or db/global) `SELECT` (`column = ""`), while keeping MySQL wire `org_table == ""` and checking ordinary columns before `_tidb_rowid`. Zero-privilege users fail with `1142` (R30); partial-column `SELECT(a)` users fail with `1143` for column `_tidb_rowid` once all ordinary columns pass. | Prevents partial-column users from reading internal physical row IDs; owner decision 2026-11-26 (D5 option A, R32, #438). |
| Column privileges in a `LATERAL` join's `ON` clause (R36) | `buildJoin` switches the column-privilege check on while it rewrites an ordinary `JOIN ... ON`, but `buildLateralJoin` does not, so the `ON` clause of a `LATERAL` join registers no column privilege: a user with only `SELECT(a)` on `t1` can reference `t1.b` in `t1 JOIN LATERAL (...) d ON t1.b = d.x`. | The `ON` clause of a `LATERAL` join is checked like an ordinary `JOIN ... ON`: a user without `SELECT` on a referenced column fails with `1143`. Takes effect with the `LATERAL` join builder (part C of the join-building block `D09.3`); `LATERAL` is not parsed by tidb-rs yet. | Closes a column-privilege bypass in the same direction as R29-R32; owner decision 2026-11-28 (option B, R36, [#482](https://github.com/dulao5/tidb-rs/pull/482)). |
| Unported authentication & login-restriction features (fail-closed) | Supports non-native plugins (`caching_sha2_password`, `tidb_sm3_password`, `auth_socket`, `tidb_auth_token`, LDAP), `REQUIRE SSL/X509/CIPHER/SAN`, password expiration with optional sandbox mode (`disconnect_on_expired_password = OFF`), failed-login account lockout, per-account resource limits (`max_user_connections`), reverse-DNS hostname matching, PROXY protocol / `tidb_session_token` migration (TiProxy), and `SET ROLE`. | Password expiration (`password_expired = 'Y'`, per-account `password_lifetime`, `@@global.default_password_lifetime` watched via etcd `/tidb/sysvars` + 30 s fallback, and Go `AddDate`/`Before` local-timezone calendar-day arithmetic) is supported and returns Go's `1862 (HY000)` after password and `Account_locked` (`3118`) checks; sandbox mode (`disconnect_on_expired_password = OFF`) is out of scope on the read-only node (cannot execute `SET PASSWORD` / `ALTER USER`), so `tidb-rs` always behaves as Go's default `disconnect_on_expired_password = ON`. Until each remaining feature is ported, `tidb-rs` **fails closed** (refuses login with `1045`) for accounts with `plugin` other than `mysql_native_password`/`''` (including empty-password `caching_sha2_password` and `tidb_sm3_password` accounts), `mysql.global_priv` `REQUIRE SSL/X509/CIPHER/SAN` or broken JSON, unparseable `password_lifetime` / `default_password_lifetime`, or failed-login lockout policy/state in `User_attributes`. Host matching checks literal IP/wildcard/netmask/loopback only (no reverse-DNS lookup; IPv4-mapped `::ffff:` addresses are normalized to IPv4); PROXY protocol, `tidb_session_token`, and `SET ROLE` are not supported yet (default roles are activated on login). Per-account connection/rate quotas (`max_user_connections`, `max_connections`, `max_questions`, `max_updates`) are not enforced on the read-only node. | Prevents silent fail-open authentication bypass or weakened security controls before remaining D04.1 auth plugins are ported; strict fail-closed merge accepted by owner (2026-11-28), with [#487](https://github.com/dulao5/tidb-rs/issues/487) / [#535](https://github.com/dulao5/tidb-rs/issues/535) (`password_last_changed` exact expiration & `1862`) landed and `caching_sha2_password` login in progress. |

## New stack (first vertical slice) differences

| Area | v8.5.8 behavior | tidb-rs behavior | Reason |
|---|---|---|---|
| Statistics loading points of the optimizer (`CollectPredicateColumnsPoint`, `SyncWaitStatsLoadPoint`) | Every user query records its predicate columns (column stats usage) and waits for the sync load of the statistics it needs. v8.x `tidb_analyze_column_options` defaults to `PREDICATE`, so auto-analyze collects statistics for the recorded predicate columns. | On the new stack both rules return the plan unchanged: only pseudo statistics exist there, nothing is loaded and **no predicate column is recorded**. Queries executed only on the new stack therefore never mark their columns, and auto-analyze (with the default `PREDICATE`) may never collect statistics for those columns. | The new stack has only pseudo statistics until the statistics handle (D11.2) is ported (VS1 plan §3.2); D09.13 spec §3. |
| Plan replayer capture (`PLAN REPLAYER CAPTURE`, `mysql.plan_replayer_task`, `tidb_enable_plan_replayer_capture`, `tidb_enable_plan_replayer_continuous_capture`) | Each Go TiDB node loads the capture tasks and dumps a plan replayer file when a statement's SQL / plan digest matches a task. | **Known limitation: tidb-rs nodes do not execute capture tasks.** Statements executed on tidb-rs are not captured, neither on the new stack nor in the prototype fallback; only statements on Go TiDB nodes of the cluster are. The variables are accepted and the capture check runs, but no task is ever loaded. | The plan replayer handle (task collector and dump worker) is not ported; D12.0 tasks "plan replayer capture check". |

## TiKV client gaps (client-rust fork, ADR 0008)

Gaps of the TiKV client against client-go, tracked in [`specs/D07.1-store/client-go-parity.md`](../specs/D07.1-store/client-go-parity.md); listed here only when a user can see them.

| Area | v8.5.8 behavior | tidb-rs behavior | Plan |
|---|---|---|---|
| `tidb_replica_read` (`follower`, `leader-and-follower`, `closest-replicas`, …) | Reads go to followers / the closest replica as set. | **Accepted but ignored**: every read goes to the leader, silently. Results are the same; the read load and cross-AZ traffic are not. | Fix item in the parity table (§3, replica read). Until then, `SET` of a non-`leader` value should return a warning (also a fix item). |

## Transitional gaps (until the session layer is ported)

tidb-rs still uses its prototype session layer until block D05.3. Until then:

- `SET GLOBAL` is not supported in the prototype session, so `tidb_redact_log` cannot be turned on in tidb-rs itself (`SET SESSION` is rejected by the fix above). Values set with `SET GLOBAL` on a Go TiDB in the same cluster are stored but not yet reloaded by the prototype.

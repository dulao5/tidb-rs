# tidb-rs 分阶段愿景

本文整理项目负责人 2026-10-22 以来在讨论中提出的愿景和阶段划分，作为后续计划的总纲。每条后面注明出处日期。具体排期见总计划（#54）和路线图（`specs/ROADMAP.md`），本文只讲"往哪里去、按什么顺序去"。

## 一句话

用 Rust 重写 TiDB 的 SQL 层：先做一个只读、与 Go TiDB 行为一致的版本，能在同一个集群里和 Go TiDB 并存、对照；再跟上上游、支持写入，最终取代 Go TiDB；之后做 Go 难以做到的事情，包括更高的性能、多种数据库协议，以及更好地利用现代硬件。

## 阶段一：可行性原型（已完成，2026-10）

- **出发点**（10-22）：以一个固定版本的 TiDB 为基础，从零做一个只读、只支持 autocommit 读的 Rust 版本。服务器框架、访问 PD 的代码和工程规范参考 TiKV；TiDB 依赖的 client-go 换成 Rust 实现；其他依赖在 TiKV 或 Rust 生态里找替代品。
- **原型范围**（10-22、10-23）：MySQL 协议服务器、SQL 解析、执行计划、统计信息、访问 TiKV 并返回结果，以跑通 sysbench OLTP read-only 为目标，不做悲观事务。
- **原型目标**（10-27）：在 oltp_read_only 场景下性能与 Go TiDB 拉平，并弄清楚为此需要从 Go 那边拿哪些库和功能。
- **结果**：原型在 sysbench 只读场景达到 Go 的 1.0–1.2 倍，结果与 Go 一致。负责人在 11-01 判定原型验证成功。

## 阶段二：有计划的整块移植，做出只读版本（进行中）

- **方法转向**（11-01）：
  - 不再为了让个别测试通过而自行编写代码，否则会离 Go 越来越远；
  - 也不为了修测试零散地引入上游模块，否则会变成在 TiDB 代码地图上做深度优先探索，质量不可控；
  - 改为先规划宏观模块，在"功能"之上再建一层"领域 / 功能块"，用它组织功能和测试用例、制定计划，一个阶段一个阶段推进，始终保持与 Go TiDB 的逻辑一致；
  - 允许部分测试暂时不通过，但整体进度和质量要可控。
- **测试和功能入库**（10-22、10-27）：从 TiDB 的单元测试和端到端测试反推功能，整理成任务与进度数据，入库管理并可视化。
- **这一阶段的目的之一**（11-16）：实验一套"安全重构的方法"。不追求一步到位的最优实现，避免行为变更；更好的实现方式记为后续待办。
- **要达到的状态**（10-27）：先得到一个与 Go 性能基本一致的 Rust 版本，再得到一个功能完善的只读版本。
- **现在的落地方式**：
  - 移植规则写在宪章（`CONSTITUTION.md`）里：Go TiDB v8.5.8 是规格，偏离必须登记为例外并经负责人确认；
  - 只读范围的 Go 代码分到约 95 个功能块，分五个阶段（P1 地基、P2 读取链路、P3 优化器、P4 执行器、P5 外围）；
  - 用六个检查点衡量进度（见附录）。

## 阶段三：集中 QA（只读版本移植完成后）

- **来源**（11-01）：大块功能移植稳步完成后，转入集中 QA。
  - 端到端测试；
  - 逐个审阅 TiDB 仓库的 issue，使行为一致。
- **开头先上的两类测试**（11-20）：与 Go TiDB 的随机 SQL 差分测试，以及不需要参照实现的 TLP / NoREC 蜕变测试（#266）。条件是 P3 已有一定覆盖，不必等只读版本全部完成。

## 阶段四：跟上上游，与 Go TiDB 等价替换（只读）

- **追上游**（10-22）：做出与基线版本等价的 Rust 版之后，拉取 TiDB 上游的新代码，把差量作为新的开发任务，再分析、再开发，一轮一轮追上上游的进度。
- **目标**（10-22）：与 Go TiDB 能够等价替换、做 AB 对比测试，或者作为集群里的一个共同服务组件去测试和试用。
- **影子读**（11-13）：在已有的 Go TiDB 集群里加入 tidb-rs 只读节点，由 TiProxy 路由。同一条查询在 Go 和 Rust 上各执行一次，只把 Go 的结果返回给用户，tidb-rs 只做结果一致性验证和诊断记录。为此需要 TiProxy 支持时间戳的缓存和批量获取，并允许两边使用 TiProxy 指定的同一个读时间戳。

## 阶段五：支持写入，取代 Go TiDB

- **来源**（10-27、11-14）：只读版本之后做支持写入的版本，包括 DML、DDL 和事务。全部实现后，Go TiDB 退役。

## 阶段六：超越 Go TiDB

以下是负责人提出的长期方向。标注"本里程碑"的需要在现在的只读阶段就落实或留出设计余地，其余是将来的事。每一项都有对应的架构审核 issue（标签 `arch-review`）。

**性能**
- **Go 难以实现的优化**（10-27，长期）：例如不依赖 GC 的对象池，获得进一步的性能提升。
- **计划级 JIT**（11-23，将来）：编译整条执行流水线（算子融合加表达式），不只编单个表达式；分层执行（先用现有的向量驱动解释执行，按预测行数决定是否编译，编译失败一律退回）。前提：表达式框架（N4）、列格式（N5a）、实例级 plan cache（A3）落地，并且 TPC-H / ClickBench 的 profile 证明根节点的表达式和算子占 CPU 的比例足够高。OLTP 不在目标内；TiKV 协处理器侧的 JIT 和融合作为对 TiKV 的建议。现在先做不依赖 JIT 的配套：#311、#312、#313、#314。
- **现代 CPU 指令集**（11-14，本里程碑）：SIMD 等（#170；调研结论见 #255）。
- **NUMA 与 64 核以上的大机型**（11-14，将来要，本里程碑留设计余地）（#171）。
- **GPU**（11-14，将来要，越早越好）（#172）。
- **资源管控**（11-13）：Go 版做得不够好，Rust 上也许能做得更好。

**多种数据库，一份逻辑**
- **迁移 PostgreSQL 和 Oracle**（11-14，Go TiDB 退役之后）：方便客户把 PG 和 Oracle 数据库迁到 TiDB（#166）。范围限于 SQL 语法和协议，不包括它们的工具和外围功能。
- **语法超集和功能超集**（11-14）：MySQL、PG、Oracle 的用户迁到 TiDB 后能用上新特性；超集在 TiDB 里逻辑上只有一份，而不是三份（#167）。
- **多租户**（11-14）：将来 tidb-x-rs（多租户、keyspace）实现后，可以让一个租户绑定一种协议，超集的具体语法按租户分别落地，逻辑保持统一（#168）。

**新功能**
- **IN 列表和多行 INSERT 的自适应**（11-14，本里程碑）：`WHERE IN (?, ?, ?)` 的元素数、`INSERT VALUES (), (), ()` 的行数不同时，共用一个 digest 和一份执行计划（#169）。
- **原生 ARRAY 类型**（11-14、11-17）：独立需求（#169）。
- **像 DuckDB 那样直接读文件**（11-14）：直接读 S3 和本地文件当表用，与 TiKV 数据、JSON table 函数等一起做关系运算（#173）。
- **高性能的 JSON_TABLE**（11-17）。
- **函数计算与关系运算打通，像 DuckDB 那样**（11-17）：函数的结果可以是数组或 map，再展开成关系数据（类似 `UNNEST`、表函数、`LATERAL`），与其他表一起做 join 等关系运算。和原生数组、JSON_TABLE、直接读文件是同一个方向。
- **tidb-server 内统一的 buffer pool**（11-17）：各类缓存和算子内存由一个池统一管理和分配。
- **高性能的缓存表**（11-17）：TiDB 的缓存表（`ALTER TABLE ... CACHE`）在 tidb-rs 上做得更快。

**已经确定的技术取舍**（11-13）
- 只做 infoschema v2 的缓存；v1 是技术负债，不再关心。
- 只做实例级执行计划缓存（已 GA）；会话级是技术负债，不再关心。

## 贯穿始终的原则

- **Go TiDB 是规格**：行为与 Go 一致，偏离要登记、要经负责人确认。Go 本身的缺口照 Go 移植，单独记录、与内核团队讨论（标签 `go-gap`）。
- **能与 Go TiDB 共存**：tidb-rs 节点可以加入现有的 Go TiDB 集群，对照、影子读、逐步替换。
- **进度和质量可控**：按计划整块推进，用差分测试和每周构建度量，不靠测试摸索。
- **门禁本身要可信，性能从现在起就是门禁**（11-20，采纳 pgrust 经验，见 ROADMAP 第 6 节）：覆盖率必须做分母普查、配负对照，回退到原型的语句不算进度；新栈不得慢于 Go（≤1.0×）。arena + 零 drop 内存纪律到性能阶段按门禁数据决定（#267）。

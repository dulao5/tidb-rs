# 预处理点查的性能：与 Go TiDB v8.5.8 比较（性能门禁的第一项）

状态：2026-11-24，基于 main `58b62a8`。本文是性能门禁（issue 263）第一项的测量记录：怎么测、改之前和改之后的 profile、每项改动的前后数字、与 Go 的结构差异、剩下的差距。

## 1. 结论

| 指标（新栈 / Go，Go 打开实例级 plan cache） | main `58b62a8`（3 轮） | 本次改动后（5 轮，§5.1 运行 C） | 门槛 |
|---|--:|--:|--:|
| 吞吐，1 线程 | 0.96 | 0.99（区间 0.95–1.04） | ≥ 1.0 |
| 吞吐，8 线程 | 0.94 | 0.98（区间 0.96–0.995） | ≥ 1.0 |
| p50 延迟，1 / 8 线程 | 1.04 / 1.07 | 1.02 / 1.04 | ≤ 1.0 |
| p99 延迟，1 / 8 线程 | 0.96 / 1.02 | 0.82 / 0.97 | ≤ 1.0 |
| 每条语句的分配次数 | 412（Go 223） | 334（Go 223） | ≤ 1.0 |

- **吞吐和延迟**：新栈自己的 QPS 提高约 6–10%（1 线程 8057 → 9074，8 线程 28727 → 31480），1 线程与 Go 持平（在噪声内），8 线程还差约 2%（5 轮的区间不含 1.0，按规则是 FAIL），p50 差 2–4%，p99 好于 Go。按每条语句消耗的 CPU 算，新栈已经不比 Go 多：1 线程 61 µs 对 Go 75 µs，8 线程 94 µs 对 95 µs（进程 CPU 时间 / 语句数，同一负载）。剩下的延迟不在 CPU 上，而在 gRPC 请求经过的几个任务之间的交接（§6 第 1 条）。
- **分配次数**：412 → 334，仍是 Go 的 1.5 倍。剩下的大头是 TiKV 客户端和 gRPC（约 95 次，Go 整条语句才 223 次）、PoC 路由的检查点（约 30 次）和列定义（约 32 次）。要降到 Go 以下需要设计上的改动（§6）。

## 2. 怎么测（门禁的定义和噪声规则）

### 2.1 负载和环境

- 本机 tiup playground v8.5.8（1 PD、1 TiKV、1 Go TiDB，`security.auto-tls`），sysbench 1.0.20 `oltp_point_select`，`--db-ps-mode=auto`（服务端预处理语句，自动提交），1 张表 1 万行、4 个 region（`scripts/sysbench-prepare.sh -t 1 -s 10000 -r 4`，经 Go TiDB 写入）。
- 新栈：`tidb-server --new-stack=fallback`（默认的 `--tikv-connections 4`，与 Go 的 `grpc-connection-count` 默认值相同），与 Go 连同一个集群。
- Go：`SET GLOBAL tidb_enable_instance_plan_cache = ON`（负责人选定的参照）；另测一次 Go 默认配置（会话级 plan cache）作参考。
- 同一台机器上跑 TiKV、两个 TiDB 和 sysbench，A（Go）与 B（新栈）不同时跑。

### 2.2 门禁脚本

`tools/perf/point_select_gate.py`（不需要 CI，没有固定的基准机；在有 playground 的机器上手动跑）：

```sh
scripts/playground.sh start -t perf -o 25000
scripts/sysbench-prepare.sh -P 29000 -t 1 -s 10000 -r 4
cargo build --release -p poc-server --bin tidb-server
tools/perf/point_select_gate.py --go 127.0.0.1:29000 --go-status 127.0.0.1:35080 \
    --rs-bin target/release/tidb-server --pd 127.0.0.1:27379
# 只看分配：加 --allocs-only；Go 默认配置：--go-instance-cache off
```

脚本自己启动新栈（每次新进程），先各预热 5 秒，然后跑 `--rounds` 轮（默认 3），每轮 1 线程和 8 线程各 20 秒，A、B 先后顺序逐轮交替（AB、BA、AB），让机器的慢变化对两边一样。退出码 0 = 全部通过，1 = 有指标不过，2 = 测量本身失败。

- **延迟**：`tools/perf/point_select_lat.lua` 给每条语句计时（Homebrew 的 sysbench 在 Apple Silicon 上所有百分位都报 0），桶宽约 0.5%；p50 / p99 取所有轮合并后的直方图。
- **分配次数**：Go 用状态端口的 `go_memstats_mallocs_total`，10 万条语句前后之差，减去之前 5 秒测得的空闲速率；新栈用 jemalloc 退出时打印的 `nrequests`（small + large），一个进程跑 10 万条，另一个进程跑 1 条后空等同样长的时间，两者之差 / 99999。

### 2.3 噪声规则

- 每一轮给出一个配对比值（这一轮的 B / A）。门禁值是所有轮的总和之比（吞吐：B 的 QPS 总和 / A 的；延迟：合并直方图的百分位之比）；分配次数测一次（是计数，重复误差约 1%）。
- 同时打印每轮比值的 95% 置信区间（t 分布，自由度 = 轮数 − 1）。
- 判定按门禁值与负责人的门槛比较（吞吐 ≥ 1.0；p50、p99、分配 ≤ 1.0）。置信区间跨过门槛时标"within noise"：**within noise 的 FAIL 仍是 FAIL**，用 `--rounds 5` 重跑来判定；within noise 的 PASS 算 PASS。
- 本机的波动：同一个 Go 进程，1 线程在不同时间测得 8400–9500 QPS，8 线程 30100–32500，即单次运行约 ±5%。这也是为什么规则用交替顺序和配对比值，而不是两边各跑一次。

### 2.4 profile 工具

- 分配：`tools/perf/alloc-profile.sh build` 把计数分配器（`tools/perf/allocprof.rs`，按调用栈计数）编进一个单独的二进制（`target/allocprof`，普通构建里没有它）；`run -p <pd>` 跑 2000 条预热、记录 2 万条，`tools/perf/alloc_report.py` 按区域、调用点汇总成"每条语句的分配次数"。
- CPU：macOS 的 `sample <pid> 10`（8 线程负载下），`tools/perf/cpu_report.py` 按区域统计"忙碌样本"（去掉线程空等的样本）的占比。各区域会重叠（一个样本可以同时属于"TiKV 客户端"和"网络系统调用"），所以加起来不是 100%。

| # | 提交 | 改了什么 | 前 → 后 |
|--:|---|---|---|
| 1 | 内存跟踪器 | `Tracker.bytesLimit` 改成一个 `AtomicI64`（只存硬上限，软上限读时按 Go 的公式算出）；`Tracker.Killer`、`SQLKiller.lastCheckTime` 改成互斥锁保护的值 | `arc_swap` 0.07 → 0；8 线程 0.942 → 0.954 |

## 6. 剩下的差距和原因

1. **延迟里的任务交接（需要改 gRPC 传输）**。新栈的 CPU 已不比 Go 多，1 线程的延迟仍与 Go 相同，差别在等待：一次 TiKV 读要经过 tonic `Channel` 的缓冲任务（`tower::buffer`）、hyper 为每个请求体新开的发送任务、h2 连接任务，回程再唤醒连接任务，每次交接都可能跨线程。client-go 用批量的流（`BatchCommands`）和固定的收发 goroutine。去掉这些交接要在 client-rust 里绕开 tonic `Channel`（直接用 hyper 的 HTTP/2 连接，自己处理重连、keepalive、超时），或实现批量流；这些都改变连接管理，属于设计改动，本次没有做。
   一个旁证：把新栈的 tokio 工作线程从默认的 12（= CPU 核数，与 Go 的 `GOMAXPROCS` 相同）减到 4（`TOKIO_WORKER_THREADS=4`，代码不变），同一门禁 3 轮：8 线程 **1.027（区间 1.005–1.049，PASS）**，p50 0.985；1 线程 1.020（噪声内）。空闲的工作线程越多，每次交接越可能唤醒一个睡眠的线程再由它去偷任务。本机上 TiKV、sysbench 和两个 TiDB 共用 12 个核，这个数字不能直接推到独占机器上；默认线程数是运行时拓扑（N3）的决定，本次没有改，请负责人决定是否要按核数以外的规则设默认值，或在 tokio 里减少唤醒（例如让 gRPC 连接任务与发起请求的连接任务留在同一线程）。
2. **TiKV 客户端的分配（约 95 次）**。其中约 30 次在 tonic / h2 / hyper（请求头、请求体、流的状态），约 11 次是 region 缓存每次复制 `Region`（含 peers、起止 key），约 4 次是复制请求的 `Context`。前者是 tonic 的一元调用本身的成本；后者要把 client-rust 的 region 缓存改成共享（`Arc`），也是 client-rust 的结构改动。
3. **PoC 路由的检查点（第 6 项后约 30 次分配，CPU 约 1.6%，另有丢弃旧语句上下文的约 2%）**。检查点在每条语句开始时复制会话变量（约 285 个标量字段，其中十几个是字符串，以及非标量状态），以便回退时恢复。我们验证了"与上一条语句的检查点相同就复用"：不可行，`DurationCompile` 等标量和 plan cache 参数每条语句都变。要真正做到写时复制，需要把会话变量按"很少写的部分 / 每条语句写的部分"拆开，或让生成器（tracker 的 `rsgen`）生成逐字段的 `clone_from`；回退语义不变。PoC 退役后这部分整个消失。
4. **表达式上下文每次用都新建（约 14 次）**。N2 的设计：上下文是会话在某一时刻的视图，每次交出时新建（Go 每个会话一个、实时读会话）。复用它需要判断视图是否仍然有效，属于 N2 的设计改动。
5. **Go 默认配置（会话级 plan cache）比实例级缓存稍快**：1 线程 0.96。新栈只有实例级缓存（A3 的决定），这一项不在门禁的参照里。

## 7. 与 Go 的结构差异（本次引入，均为性能偏离，行为不变）

1. 内存跟踪器：`bytesLimit` 只存硬上限、软上限读时算出（Go 存 `*bytesLimits`）；`Killer` 与 `SQLKiller.lastCheckTime` 用互斥锁，不用 `ArcSwap`（映射规则 M-SNAP 的偏离）。理由：每条语句创建和丢弃两个跟踪器，`ArcSwap` 的写入和丢弃要遍历所有线程（§3.2）。软上限：`DefMemQuotaQuery` 时与 Go 的 `DefMemQuotaQuery * 8 / 10` 相同；无上限时 Go 为 −1、这里为 0，都表示"没有上限"（只在 `> 0` 时使用），有单元测试。
2. 表达式上下文中与会话无关的六个属性提供者全进程共享（Go 每个会话建一次）。它们不带状态，只回答边界错误或固定值。
3. client-rust：单 region 的请求在调用者的任务里执行（client-rust#25）。一个行为上的细节：这个请求内部若 panic，现在直接传到调用者（以前变成 `JoinError` 错误）；panic 本身是缺陷，tidb-rs 的连接任务会捕获它。
4. 会话状态的 `AnalyzeSkipColumnTypes` 共享，SET 时整体替换（Go 是会话自己的 map）。
5. 其余改动（输出列名共享、列定义不复制、编码不变时借用、`strings.ToLower` 的快速路径）是去掉 Rust 特有的复制，结构上更接近 Go（Go 本来就是指针或原样返回）。

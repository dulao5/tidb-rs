# 例外候选：详细说明

本文是 [例外清单](README.md) 中各项的理由和建议，状态以 README 的索引表为准。

## 来源一：初版清单（A–D）

依据宪章第三条。

列说明：
- **类型**：实现例外 = SQL 行为与 Go 相同，内部重新设计；特性例外 = 特性定义与 Go 不同；范围 = 不是例外，而是"何时做"的排期问题。
- **建议**：提出时的建议；决定见 README 索引表。

### A. 实现例外（来源：roadmap 和 Go 的结构性缺陷）

| # | 内容 | 涉及的 Go 范围 | 建议 | 主要理由 / 风险 |
|---|---|---|---|---|
| A1 | **统一内存模型**：Chunk/Column 缓冲区、语句级内存区域、可计算的内存预算（按实际分配计账，替代 Go 的 `memory.Tracker` 估算） | util/chunk, util/memory, 各执行器的内存统计 | 接受；P1 先写设计 spec，P4 执行器移植前定稿 | 收益最大的一项。约束：`tidb_mem_quota_query`、OOM 行为、超限报错等用户可见语义保持与 Go 一致 |
| A2 | **执行模型**：Go 每个算子用若干 goroutine worker；Rust 保持相同的算子结构和 `Next()` 接口，worker 映射到共享线程池 | executor 中各并发算子（hash join、hash agg、index lookup 等） | 接受，作为 A1 的配套设计 | 只改调度，不改算子语义；并发度变量的含义保持 |
| A3 | **缓存类**：coprocessor cache、plan cache、schema cache（infoschema v2）、统计信息缓存，按 Rust 的内存布局和淘汰策略重做 | store/copr 缓存、planner/core 的 plan cache、infoschema v2、statistics/handle/cache | 接受，分 4 个独立 spec，各自在所属块排期时提出 | 命中与淘汰的可观测行为（如 `last_plan_from_cache`、容量变量）保持一致 |
| A4 | **JSON**：二进制 JSON 格式保持兼容（与 TiKV 及存储一致），解析、序列化、路径求值按 Rust 重新实现 | types/json_binary*, expression 中的 JSON 函数 | 接受 | 函数语义、错误、排序和比较规则与 Go 一致；用 Go 生成的测试向量对照 |
| A5 | **SIMD / 向量化求值**：保留 Go 向量化函数的语义，实现上允许使用 SIMD | expression 中的 vectorized builtin | 接受，但按函数族逐个启用，每族先有忠实移植版本作为对照基准 | 防止为性能改动语义 |
| A6 | **读取路径**：coprocessor 响应零拷贝解码、批量请求等 | store/copr, distsql | 接受，P2 时提出 | 协议不变，只改实现 |

### B. 特性例外（来源：Go 已废弃 / 计划废弃 / 非默认路径）

| # | 内容 | v8.5.8 现状 | 涉及规模 | 建议 |
|---|---|---|---|---|
| B1 | **静态分区裁剪**（`tidb_partition_prune_mode=static`） | 默认 `dynamic`；设成 static 时 Go 会给出"已废弃"的 warning | planner 中 static 分区的 union 计划路径 | 不移植。设置 static 时报错 |
| B2 | **v1 统计信息**（`tidb_analyze_version=1`，CMSketch 等 v1 专用部分） | 默认 2；设成 1 时有废弃 warning | statistics 中 v1 专用代码 | tidb-rs 不执行 ANALYZE，只读取统计信息。建议只支持读取 v2；若集群里的表还是 v1 统计，就当作没有统计信息处理（与 Go 的伪统计路径一致）。这是用户可见的降级，正式 spec 中需写明 |
| B3 | **旧 cascades 优化器**（`pkg/planner/memo`、`pattern`、`implementation`） | 实验性，`tidb_enable_cascades_planner` 默认 OFF；上游已经另起了新实现 | 约 1.5k 行 | 不移植 |
| B4 | **新 cascades 优化器**（`pkg/planner/cascades/*`） | 实验性，默认 OFF，仍在开发中 | 约 5.2k 行 | 暂不移植，在上游同步时再评估。开启该变量时报错 |
| B5 | **代价模型 v1**（`tidb_cost_model_version=1`） | 默认 2；没有正式废弃 | `plan_cost_ver1.go` 约 1.3k 行，加上各算子中的 v1 分支 | 不移植，设置为 1 时报错。这是"非默认路径"而非"已废弃"，正式 spec 中需说明理由 |
| B6 | **已废弃的并发度变量**（`tidb_hash_join_concurrency` 等 9 个） | 废弃但仍然生效，并给 warning | 很小 | **不作为例外**，按 Go 照搬（成本很低，还能避免兼容问题）。列出来只是为了说明判断标准 |
| B7 | **始终开启的开关**（`tidb_enable_table_partition`、`tidb_enable_global_index`、`tidb_enable_exchange_partition` 等） | 只能是 ON，设置时给 warning | 很小 | 同 B6，照搬 |

## 来源二：Rust 有优势的其他领域（N1–N8）

在 A1–A6 之外。判断标准有三条，**同时满足**才列为例外：
1. **收益可测量**：CPU、内存、尾延迟、可靠性等方面，有明确的指标和基准；
2. **行为契约不变**：SQL 结果、错误、warning、系统变量语义仍与 Go 一致，能用现有的对照测试验证；
3. **改动集中**：偏离限制在一个"框架"层，框架之上的业务逻辑（函数体、规则、代价公式）仍按 L1 移植。

第 3 条是关键。例外要改的是"承载方式"，不是"业务逻辑"。否则例外会扩散成新一轮的自创代码。

### 第一类：不是"可选优化"，而是 Go 的写法在安全 Rust 中无法照搬，必须先设计

这三项不论是否追求性能都绕不开，**会影响之后的每一个块**。所以建议在 P1 之前作为"基础设计 spec"定下来，按例外流程由项目负责人确认。

| # | 内容 | Go 的现状 | Rust 的做法（建议） | 收益 |
|---|---|---|---|---|
| N1 | **计划树和表达式树的表示与所有权** | 指针互相引用的可变树，节点通过 interface 多态；列靠 `UniqueID` 标识；规则在原地改树，靠 `Clone` 复制子树 | 每条语句一个 arena，节点用下标引用；表达式不可变、可共享；规则按 Go 的步骤原样改写，只是把"改指针"换成"改下标" | 规则代码仍可逐行对应 Go；没有循环引用和泄漏；整棵树随语句一次释放 |
| N2 | **会话和语句上下文的共享状态** | `SessionVars`、`StatementContext` 是巨大的可变结构体（`session.go` 里有 22 处锁或原子操作），被 KILL、processlist、指标采集等多个 goroutine 并发访问，TiDB 历史上有大量 data race 相关的 bug | 按访问方式拆分：本连接独占的可变部分；跨线程只读的快照（processlist 读这个）；少量原子字段（kill 标志、内存统计）。由编译器保证没有数据竞争 | 一整类并发 bug 在编译期消失；processlist 等读取不再需要锁 |
| N3 | **并发、取消与错误边界**（扩展 A2） | goroutine + channel + context 取消；执行器里大量 `recover()` 把 panic 转成错误；Close 的顺序靠约定 | 共享线程池 + 显式取消令牌；`Result` 传递错误，只在线程边界用 `catch_unwind`；算子的 Close 由所有权（Drop）保证 | 取消和资源释放可预期；不会出现泄漏的 goroutine |

### 第二类：收益明确的"实现例外"（行为不变）

| # | 内容 | Go 的瓶颈 | Rust 的做法 | 预期收益 / 风险 |
|---|---|---|---|---|
| N4 | **表达式求值框架：单态化和静态分发**（与 A5 SIMD 互补） | 每个内置函数是 interface，每行求值走动态分发（`evalInt`/`evalString`…），向量化版本也要逐列分发；常量参数没有特化 | 用泛型按参数类型、是否常量生成专门版本，编译期决定调用路径（TiKV 的 `rpn_fn` 已经证明可行）。**函数体本身仍按 Go 的 L1 移植**，只有外层调度框架不同 | 表达式密集的查询 CPU 明显下降。风险在于框架和 Go 差别大，需要逐函数对照测试兜底 |
| N5 | **值的表示和零拷贝** | `Datum` 每个 72 字节，字符串和 `any` 带来额外分配；从 coprocessor 响应解码时要复制 | 用紧凑的 enum；字符串和字节按引用借用响应缓冲区；chunk 列直接指向收到的数据，到真正需要时才复制 | 读取路径分配大幅减少；与 A1、A6 一起设计 |
| N6 | **哈希聚合、哈希 join、排序的数据结构** | 分组键先序列化成 `[][]byte` 再放进 `map[string]`（`codec.HashGroupKey`）；哈希表里的 key 和 value 都是独立的堆对象 | 开放寻址的哈希表（SwissTable 一类），定长键内联存放，变长键放 arena；排序用规范化的排序键加基数排序；落盘（spill）纳入 A1 的统一内存预算 | 聚合、join、排序的 CPU 和内存都下降，落盘时机可预测。**注意**：没有 ORDER BY 时，输出行的顺序可能和 Go 不同（Go 本身也不保证顺序），对照测试要按集合比较 |
| N7 | **结果集编码和网络层** | chunk → 每行 Datum → 编码成协议包，中间多次分配；每个连接一个 goroutine | 从 chunk 直接编码成协议包，缓冲区复用；异步 IO，少量线程服务大量连接 | 大结果集的吞吐，以及高并发短查询的延迟和内存 |
| N8 | **系统变量注册表和建连成本** | 每个会话复制一份几百个变量的 map 和大结构体，取值靠字符串查找 | 编译期生成的静态注册表；会话里只保存改过的变量（写时复制）；取值用强类型字段 | 建连成本和每个连接的内存下降。变量的取值范围、校验、warning 仍按 Go 照搬 |

### 第三类：不建议作为例外（Rust 没有本质优势，或会破坏一致性）

| 内容 | 理由 |
|---|---|
| 优化器的规则、代价公式、基数估算 | 这是"行为"本身。Rust 写得再好，也会让计划和 Go 不一致；计划级对照测试也会失去意义 |
| 系统变量和 hint 的语义、错误码和文案、warning | 用户可见的契约 |
| 统计信息的数学计算（直方图、TopN、估算） | 同上；数据结构的内存布局可以归入 A3 |
| collation 和字符集规则 | 必须逐字节一致。性能优化（如排序键缓存）可以放在 N6 内部 |
| parser | 已经是语法表同构移植，再改没有收益 |
| 对象池等"绕开 GC"的技巧 | Rust 没有 GC，不需要；照搬反而增加复杂度。这类 Go 代码移植时直接去掉，按 L2 登记 |

### 排期建议

- **N1、N2、N3 加上 A1（内存模型）**：P1 之前作为"基础设计 spec"一起定。它们决定所有块的代码形态，晚定就要返工。
- **N4**：P1 表达式框架移植时定下。
- **N5、N6**：分别在 P2（读取路径）和 P4（执行器）开始前定下。
- **N7、N8**：P2 时定下。
- 每一项在 spec 中先写明"可测量的目标"（基准 SQL、指标，以 Go TiDB 的同一场景为对照）。验收时达不到目标的，按 L1 重新移植那一部分。
